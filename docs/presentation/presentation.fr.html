03 — Le sujet

Un agent qui agit, et la question de son autorisation

Savant Azurian est un prototype d'agent IA personnel, à parler ou à écrire, construit sur Microsoft Azure avec LangGraph et Microsoft Foundry.

Il lit et modifie un espace Notion, exécute des commandes sur un serveur Linux, interroge des documents de projet et cherche sur le web.

Né comme un exercice d'apprentissage de l'IA agentique et du cloud sur un cas réel, il s'organise autour d'une question : quand une IA a de vrais outils, qu'est-ce qui rend une action autorisée ?

04 — Le problème et la réponse

Un agent qui agit, sous double verrou

Un assistant qui peut écrire dans un espace Notion ou lancer des commandes sur un serveur est utile, et dangereux : une seule erreur a des conséquences réelles.

Le risque est maximal quand il vient de lire un contenu non fiable, comme une page web, puis passe à l'action.

1
AccèsLe propriétaire laisse l'agent entrer dans un espace de travail.
2
AccordLe propriétaire dit oui à une action précise, dans un message ultérieur. Un second appel IA vérifie que c'est bien un oui.
Validé en réel
Notion · serveur Linux en SSH · chaîne vocale
Testé avec des services simulés
Documents de projet · recherche web · projets et sessions
Non construit
Gmail · mémoire des sessions passées
Pourquoi ce casUn agent qui agit est le cas où une seule erreur coûte cher : c'est là que la conception compte le plus.

05 — L'architecture

Trois briques, un seul chemin vers les outils

Client webTourne sur l'ordinateur du propriétaire. L'hébergement Azure a été écarté (ADR-0010).
Backend (BFF)Le serveur entre le client et l'agent : porte réservée au propriétaire, connexion Notion, projets, envois. Il fixe le projet ; le modèle ne le choisit jamais.
Agent hébergéLe graphe LangGraph servi sur Foundry. Il atteint Notion, la VM et les documents ; Cosmos DB ne concerne que le backend.
Pourquoi ce choixStatic Web Apps était exclu par la politique de régions de l'abonnement : le client web tourne donc en local.

06 — Le fonctionnement

Une écriture Notion, de la demande au résultat

Tour 1
01

Le propriétaire demande

« Ajoute cette ligne à ma page Sandbox. »

Tour 1
02

La politique classe l'outil

Seul un outil en lecture seule s'exécute librement. Celui-ci est retenu : rien ne part vers Notion.

Tour 1
03

Le serveur demande

Le serveur écrit la question, pas le modèle. Une autorisation à usage unique est liée à l'opération.

Tour 2
04

Le propriétaire répond

« ui, lance »
L'accord ne peut venir que d'un tour ultérieur.

Tour 2
05

Un second modèle juge

Un appel isolé voit le message et la proposition : approuver, rejeter ou demander. Sortie invalide : rien n'est écrit.

Tour 2
06

Consommer, puis écrire une fois

L'autorisation est consommée avant tout appel réseau et jamais rendue. Une écriture, puis le résultat.

Constaté lors de l'essai réel · 25 oct. 2026

  • Écriture approuvée : un seul marqueur, vu par une lecture indépendante
  • Écriture refusée : page identique à l'originale
  • Accord rejoué : no_pending_approval
  • Autre conversation : opération inutilisable

Même principe pour le shell

Le juge répond RUN, CONFIRM ou REFUSE. Une commande confirmée ne s'exécute qu'à un tour ultérieur, une seule fois.

Pourquoi ce choixLangGraph ne reprend pas sur un simple « oui », et le modèle principal est le composant attaqué : un appel isolé juge.

08 — Quatre moments de décision

Quand la trajectoire a changé

Le consentement

ConstatUne liste de phrases fixes ne convient pas : « ui », « lance » ou « yes, for sure » doivent être compris.

DécisionUn second modèle, isolé, juge la réponse ; le backend vérifie l'opération, le propriétaire et l'expiration.

EffetÉcriture approuvée en réel le 23 oct. ; 44 cas sur 44 mesurés le 7 nov.

Un diagnostic contredit

ConstatUn rapport automatique accuse un fichier de dépendances d'avoir fait échouer un déploiement automatisé.

DécisionLire le journal d'exécution : cette étape avait réussi ; la cause était un signal SIGPIPE (code 141) dans une commande grep.

EffetCorrection d'une ligne ; rien n'a été déployé par erreur.

L'hébergement refusé

ConstatStatic Web Apps est refusé par la politique de régions de l'abonnement (RequestDisallowedByAzure).

DécisionGarder le client web en local et réserver l'accès au propriétaire par Entra ID sur le backend.

EffetArchitecture simplifiée ; la question d'hébergement reste ouverte et documentée (ADR-0010).

Une preuve incomplète

ConstatUne écriture retourne un succès, mais aucune relecture indépendante de la page n'existe.

DécisionNe pas la compter comme validée, et la lister parmi les points ouverts du rapport.

EffetEssai du 25 oct. : relecture, refus sans effet, rejeu bloqué.

Un prototype, pas un produit. Construit autour de l'abonnement d'un seul propriétaire.

Le code d'infrastructure n'a jamais été déployé. Il compile et passe le lint en CI.

Réponses lentes : de 28 à 72 s dans le test vocal.

Pas encore vérifié : révocation OAuth Notion, micro du navigateur, Safari, Firefox, téléphones. Non construit : Gmail.

Port SSH ouvert sur Internet dans l'installation de référence, protégé par une clé, une clé d'hôte épinglée et un compte dédié.
